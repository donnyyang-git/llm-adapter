LLM Adapter

本機 Gemini 對話保存器

這個專案的核心價值，是把 Gemini 的網頁版對話流程從「瀏覽器內的雲端工作流」轉成「本機受控、可追蹤、可保存、可重連」的本地流程。 它不直接呼叫 Gemini API，而是透過專用 Chrome + 本地中介層，讓使用者能在本機界面中選擇 Gemini 分頁、逐題發問，並保存 JSON / Markdown。

系統架構圖

架構說明與設計原因

1. 使用者介面層

由純 HTML + CSS + JavaScript 組成，不依賴 Node.js 構建流程。這樣可以保留極低門檻部署特性：只要有 Python、Chrome 與瀏覽器即可直接啟用。

2. FastAPI 入口層

做為 API 與狀態協調中心，統一處理 Chrome 狀態、Tab 列表、Session 建立、問題送出與 SSE。這有助於將前端邏輯與底層 Chrome 自動化完全解耦。

3. ChromeManager

專門管理本專案獨立 Chrome profile，避免污染日常使用 Chrome。此層處理啟動、重連、DevTools 端點偵測以及 profile stale lock 清理，是系統穩定性最重要的一環。

4. GeminiAdapter

負責定位 Gemini 的輸入框、訊息內容與生成狀態，實際模擬使用者在網頁上的操作。這個設計避開付費 API，直接利用已登入的 Gemini 網頁版能力。

5. ConversationService

承擔狀態機與鎖管理責任，例如 pending、generating、completed、partial、failed，並保證同一個 Tab 不會同時重送兩個問題。這樣可避免 Gemini 被重複提交。

6. ConversationStore

直接將每個會話保存為 JSON 與 Markdown，並使用原子寫入。這能防止中途中斷時破壞檔案，並保留可閱讀的歷史紀錄與可機器解析的資料。

設計理由： 專案採用「本機受控 Chrome + 本地狀態機 + 本地存檔」這種拆解方式，是為了降低風險與增加可維護性：
  • 將日常 Chrome 與專案專用 Chrome 分離，避免互相干擾。
  • 把 UI、自動化、狀態管理、儲存分層，讓問題能精準定位在某一層。
  • 將每個 turn 轉成明確狀態，避免問答連續觸發導致資料混亂。
  • 透過 SSE 與 session 儲存保持即時更新與可恢復能力。

核心資料流

步驟 動作 原因
1 使用者在本機網頁點擊 Connect Chrome 啟動專用 Chrome，避免接管一般使用中的瀏覽器。
2 系統列出 Gemini 分頁並選取 target 讓使用者在已登入的頁面中直接操作，而不是自行維護 cookie 或 token。
3 問題送至 Gemini 並記錄為 pending 先落盤狀態，避免使用者刷新或重試時資料遺失。
4 Gemini 回答被抓取並透過 SSE 更新 讓前端即時知道回答進度，不必每次手動重新整理。
5 結果保存為 JSON / Markdown 兼顧機器處理與人類閱讀，同時保留完整歷史。

為什麼這個架構適合這個專案

這個專案的需求非常明確：在本機、只使用單機、只對單一使用者、只保留本地對話、且必須避免污染日常 Chrome。因此它不適合走複雜微服務或雲端部署方案，反而適合採用「單機 Python + 專用 Chrome + local-first 儲存」的設計。這種設計的優點包括：
  • 部署成本低，不需要 Node.js 服務器或資料庫。
  • 安全邊界清楚：本機監聽 only，不對外暴露。
  • 故障定位容易：Chrome 問題、UI 問題、狀態問題、儲存問題分層清楚。
  • 可維護性高：後續若要補 recapture、timeout、readonly、事件重連，能直接疊加在現有狀態機上。

近期 Gemini Artifact 補強

多片段保存

每一輪 Gemini 回覆現在不只保存純文字與 Markdown，也會結構化保存多個 artifact，包括標題、摘要、語言、程式碼與預覽型態。

完整程式碼來源

對於 Gemini 的 code view，系統會優先從 Monaco editor model 擷取完整內容，而不是只依靠畫面上可見文字，避免 HTML / JavaScript 被截斷。

預覽策略

前端只對真正的 HTML artifact 顯示預覽 iframe；一般文字回覆或單純程式碼片段不再顯示空白預覽框。

附圖保存

回覆卡片截圖會落到 data/conversations/_artifacts，方便後續回看 Gemini 當時的畫面編排。
